# Android requirements for Recent-Recall

Checked 2026-11-02 (second pass the same day). Status per row: VERIFIED means read in a primary source in this run (developer.android.com, AOSP source, Google Help). UNVERIFIED means not confirmed by two sources; the note says what was found and what is missing. Search result snippets that were not opened do not count as sources.

| Topic | Finding | Status | Source |
|---|---|---|---|
| Accessibility service declaration | Service must declare `android.permission.BIND_ACCESSIBILITY_SERVICE`, `exported=true`, the `android.accessibilityservice.AccessibilityService` intent filter and an `android.accessibilityservice` meta-data XML. | VERIFIED | https://developer.android.com/guide/topics/ui/accessibility/service ; AOSP AccessibilityService.java class comment (https://android.googlesource.com/platform/frameworks/base/+/56a2301/core/java/android/accessibilityservice/AccessibilityService.java) |
| Global actions | `performGlobalAction()` is the call for system-wide actions such as Back and notifications. | VERIFIED | same guide (read again 2026-11-02) |
| GLOBAL_ACTION_RECENTS (behaviour) | The constant exists, value 3, documented as "Action to open the recent apps." | VERIFIED | AOSP source https://android.googlesource.com/platform/frameworks/base/+/56a2301/core/java/android/accessibilityservice/AccessibilityService.java (checked 2026-11-02) ; archived developer.android.com AccessibilityService reference listing the constant, https://stuff.mit.edu/afs/sipb/project/android/docs////reference/android/accessibilityservice/AccessibilityService.html (checked 2026-11-02) |
| GLOBAL_ACTION_RECENTS (API level) | The earlier text said "since API 21". That is probably wrong: the constant is already in very old AOSP source and in the archived reference. The exact "Added in API level" value was not visible in any page read, so do not rely on 21 or on any other number. Treat as available on all supported devices (minSdk), and guard nothing on it. | UNVERIFIED (API level only) | same two sources; the current developer.android.com reference page returned only its navigation menu |
| GLOBAL_ACTION_QUICK_SETTINGS (behaviour) | The constant exists, value 5, documented as "Action to open the quick settings." | VERIFIED | same AOSP source and archived reference (checked 2026-11-02) |
| GLOBAL_ACTION_QUICK_SETTINGS (API level and guard) | It sits in very old AOSP source, so the old text ("API 17 constant") is plausible, but the API level value was not visible in any page read. The SDK_INT >= 31 guard in the app is a conservative app decision, not a platform requirement. | UNVERIFIED (API level only) | same sources |
| Window content | `android:canRetrieveWindowContent` is only needed to inspect the UI tree. Set false here; events then carry no source node. Package name is still available on window state events. | VERIFIED (config attr, and window content described as capability in AOSP class comment), event behaviour from AccessibilityEvent reference | accessibility guide; AOSP class comment; https://developer.android.com/reference/android/view/accessibility/AccessibilityEvent |
| Event cost | `typeAllMask` is resource heavy. This app asks only for `typeWindowStateChanged`. | VERIFIED | accessibility guide |
| Overlay type | TYPE_ACCESSIBILITY_OVERLAY is available to an enabled accessibility service and does not need SYSTEM_ALERT_WINDOW. TYPE_APPLICATION_OVERLAY needs the "Display over other apps" special access. Decision: use TYPE_ACCESSIBILITY_OVERLAY. Found so far: current AOSP AccessibilityService source has a "Drawing Accessibility Overlays" section saying accessibility services can draw overlays on top of screen contents and it imports TYPE_ACCESSIBILITY_OVERLAY. Not found in a page that was read: an explicit statement that no SYSTEM_ALERT_WINDOW is needed. The WindowManager.LayoutParams and Manifest.permission reference pages returned only menus. | UNVERIFIED (explicit no-permission statement missing) | https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/accessibilityservice/AccessibilityService.java ; device check still pending |
| Foreground service | Apps targeting Android 12+ cannot start a foreground service from the background except in listed cases. This app uses no foreground service: the enabled accessibility service is bound by the system. | VERIFIED | https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start |
| Usage access | PACKAGE_USAGE_STATS needs the user to enable it in Settings. Not used: window state events give the package name already. Search snippets (a Google sample README and a reference mirror) say the same, but no full page was read, and the developer.android.com reference returned only a menu. | UNVERIFIED | https://developer.android.com/reference/android/app/usage/UsageStatsManager |
| Package visibility | Targeting API 30+ filters other apps. `<queries>` declares what you need. QUERY_ALL_PACKAGES is for rare cases (accessibility apps are listed as an example) and Google Play has a policy for it. | VERIFIED | https://developer.android.com/training/package-visibility/declaring |
| Decision on QUERY_ALL_PACKAGES | Declared, because the rules picker must list apps without a launcher icon and system apps. Only used in the picker. Sideloaded debug build, not on Play. Justification must be restated if ever published. | decision | this document |
| Reboot behaviour | An enabled accessibility service is normally rebound by the system after restart. Some devices turn services off or kill them. The app never promises persistence and shows live status. What is confirmed: AOSP says the lifecycle is managed by the system and the service starts or stops only through the user enabling or disabling it in settings. No page read states what happens at reboot, so the rebinding claim stays unconfirmed. | UNVERIFIED | AOSP class comment (lifecycle section); needs a source on reboot or on boot-time binding |
| Restricted settings (sideloaded) | On Android 13 and up, some settings are restricted for apps until the user chooses Allow restricted settings in the app's info (Settings, Apps, the app, More, Allow restricted settings). Google's own help page confirms the setting, the Android 13+ scope and gives accessibility as the example. It does not say "sideloaded" in so many words, and no second primary source was read (the Android 13 behavior changes page does not mention it). Search snippets from third party sites say it targets sideloaded installs, but those pages were not opened. | UNVERIFIED (one official source; second source missing; "sideloaded" wording not confirmed) | https://support.google.com/android/answer/12623953 (checked 2026-11-02) |
